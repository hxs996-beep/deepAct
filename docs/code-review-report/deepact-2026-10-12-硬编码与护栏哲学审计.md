## 1. 🚨 引擎替模型判定"完成"：stalled_narration 三击

> **状态：✅ 已修复（2026-10-12）**。完成语义改为角色声明（`AgentSpec.TextResult` / `[agents.x] text_result`），`Handoff.NoNudge` 更名为 `TextResult`，ratd 三角色声明之，两个完成契约互斥则启动期报错；击数提为 `narrationStrikeLimit` / `truncationStrikeLimit` / `blockedStrikeLimit`。实现与验证见 `docs/superpowers/plans/2026-10-12-guard-conflict-fixes.md` 的「执行记录」。本节保留为问题描述与证据。

**证据（主 agent 已读源码确认）**

- 入口 `engine/sub_agent.go:782`：`if len(msg.ToolCalls) == 0 {` —— 只要本轮 assistant 消息没有 tool_calls 就进入该分支。
- 依次排除：截断（`:783-796`）→ structured（`:797-819`，结构化 run 走 `submit_result` 契约）→ `NoNudge`（`:820-824`）。
- 计数与终止：`:828` `consecutiveIntermediate++`；`:829` `if consecutiveIntermediate >= 3 {`；`:832` `result.FinishReason = HandoffReasonStalledNarration`（常量 `engine/agent.go:42`）。
- 重置条件 `:1041-1043`：仅当本轮真派发过工具才清零；被闸拦截的调用不算派发。
- 注释自陈：`:825-827`“Deterministic completion (C5): a text-only reply NEVER completes through an LLM judgment call. Text-only output is narration → 3-strike nudge → stalled_narration.”

**判定依据**：连续 3 个"无 tool_calls 的 assistant 轮"——**不看 finish reason、不看文本内容、不看工具调用总数**。击数 `3` 是内联魔法数（`:829`）。

**为什么破坏哲学**：这是引擎替模型裁定"你的文本不算完成"。方向上有进步（从 LLM 文本判分退到结构化规则，去掉了 `ConclusionClassifier`），但仍属"行为理想度"判定，不是安全/不可逆/数据破坏——按 AGENTS.md 属于"能力优先"的反面。

**逃逸口不可达（决定性）**：
- `NoNudge` 字段存在于进程内 `Handoff` 结构（`engine/agent.go:82`），但**模型可见的 `HandoffToAgentParams`（`engine/agent.go:224-250`）没有 `no_nudge` 字段**。
- 全仓 grep：`NoNudge: true` 只出现在 `*_test.go`；`engine/handoff.go` 无任何 `Nudge` 赋值；`StructuredResult` 唯一来源是角色 spec（`engine/default_agents.go:103`）。
- 故 `engine/sub_agent.go:799-800` 的注释“harness roles (collab/ratd) pass NoNudge:true”**与生产代码不符**（注释漂移），实际没有任何生产路径设置它。

**具体后果（内置技能自相矛盾）**：
- `ratd` 三角色 **非结构化**：`proposerSpec`(`default_agents.go:192-200`)、`redteamSpec`(`:204-212`)、`arbitratorSpec`(`:217-225`) 均未设 `StructuredResult`；而 persona（`:237-249`）要求 `Output ONLY a CodePayload/TestPayload/decision JSON object … Nothing but the JSON object.`，`skill/builtin/ratd/SKILL.md:16,23,34` 也按"角色输出 JSON 文本、编排者落盘"设计。
- 即：**内置技能要求纯文本交付，护栏规定纯文本永不算完成**。角色正确输出 JSON 会被 nudge “use tools”，第 3 次以 `stalled_narration` 收尾（`Summary` 仍带 JSON，但 finish reason 不是 `completed`）。
- 对照：`collab` 的 `researcher` 设了 `StructuredResult: true`（`default_agents.go:171`），走 `submit_result`，**不受影响**——所以这是"能力有无"的差别，不是不可避免地要靠猜。

**最小改法**：①把 `3` 提为命名常量；②在 `HandoffToAgentParams` 暴露与 `submit_result` 等价的显式完成声明能力（模型可声明"文本即结果"），或让非结构化角色也获得 `submit_result` 通道——把"是否算完成"还给模型/角色声明，而不是靠计数猜。

## 2. 🚨 工具名白名单驱动护栏与流程（类别①②）

> **状态：✅ 已修复（2026-10-12）**。工具元数据（`Mutates` / `NovelInfo` / `Sequential`）改由工具自己声明，`MadeProgress`、批/串行划分、拦截工具排除均改由元数据 / 单一表驱动；`filePath` 别名已统一。见计划文档的执行记录。

### 2.1 `MadeProgress`（最严重）
- 位置：`engine/turn.go:855-908`，`switch c.Name` 枚举 `edit/write/apply_patch/revert/bash`（且 `statusByID[id]=="ok"`）、`read`、`read_multi`、`grep/glob`、`lsp`、`web_search/fetch`。
- 消费方：`engine/loop.go:710-733` —— `progressLoop.Check("", MadeProgress)`（实例 `loop.go:410` `NewLoopTracker(4, 6, true)`），`GuardBlock` 时 `BlockedBy:"loop_guard"` / `FinishReason:"loop_detected"` **终止 Run**。
- 失效场景：新增写类工具（`rename_file`/`delete_file`/`run_tests`/MCP 工具）连续 6 轮成功执行 → 每轮 `MadeProgress=false` → 被判定"无进展循环"并中断。
- 改法：由 `ToolSpec` 声明能力位（是否变更文件 / 是否获取新信息）驱动，而不是名字 switch。

### 2.2 破坏性/只读分类
- `engine/turn.go:766-777`：`if call.Name == "edit" || "write" || "apply_patch"` → `destructiveCalls`，否则并入 `readOnlyCalls` 并行批执行。
- 失效场景：新增破坏性工具被当只读工具并行批执行，破坏"破坏性调用串行 + 逐个展示 diff"的既有假设。

### 2.3 引擎拦截工具的 if-else 链
- `engine/turn.go:672-700`：11 个 `else if call.Name == XxxToolName { continue }`（handoff/load_skill/todo_write/ask_user/plan_task/agent_poll/agent_resume/list_agents/wait_agent/send_message/interrupt_agent/close_agent）。
- 失效场景：新增拦截工具漏加 → 该调用落入 `regularCalls` 被 `Execute` 执行 → 返回 “tool not found” → 同一 `tool_call_id` 两条 tool 消息 → 违反 API "一个 id 一个响应" → 请求 400、会话卡死。文件内 `:666-669` 注释正是描述这个坑。
- 改法：由各 `process*Calls` 返回"已处理 id 集合"，或用由常量构造的 set 替代 if-else 链。

### 2.4 key 构造与路径别名（③+⑤）
- `engine/key.go:35-61` `extractToolKey` / `:187-212` `repeatKeys` 按工具名 switch，只覆盖 `read/edit/write/read_multi/grep/glob/lsp`。
- `engine/key.go:167-182` `extractPathField` 只认 `"path"` 与 `"file_path"`（**不认 `"filePath"`**），而 `engine/turn.go:1386-1404` `extractPathFromArgs` 三者都认 → 同一路径两套结果：别名 `filePath` 下 edit/write 的重复计数与进度识别被静默丢弃。
- 改法：路径提取收敛到单一 helper；key 由工具声明目标字段。

### 2.5 子代理只读宇宙（合法保护，但形态是名字清单）
- `engine/sub_agent.go:38`：`var subAgentUniverseNames = []string{"fetch","glob","grep","lsp","read","read_multi","web_search"}`（闭集，未知=不允许）；通道工具按名放行 `:50-52`。
- 过滤按名字：`filterTools` `:1256-1300`（判定 `:1276`/`:1292` 用 `spec.Function.Name`）；执行闸 `:934` `if !effectiveSet[call.Name]`（安全边界，正确）。
- per-role 收窄清单也是名字列表：`default_agents.go:169/182/196/208/221` 均为 `[]string{"read","read_multi","grep","glob","lsp"}`。
- 判定：**属合法确定性保护**（只读宇宙是委派执行的信任边界，设计文档已论证），但形态与设计文档自陈的"可选硬化项（ToolSpec 加来源标记）"有落差。
- 失效场景：新增只读工具（如 `artifact` 只读变体）不会自动进入宇宙，须手改 `:38` 这一行，否则子代理永久看不到（静默、无报错）；反之，一个恰好叫 `read` 的用户写工具会被当只读放行（无来源校验）。
- 改法：`tools.ToolSpec`（`tools/registry.go:13-17`）加 `ReadOnly`/`Source` 元数据，宇宙校验读元数据，名字清单退化为兜底。

### 2.6 角色注册表与 enum 双源
- 内置 6 角色的 persona / ToolNames / MaxIterations / StructuredResult 硬编码（`engine/default_agents.go:144-225`，persona 常量 `:230-249`）。
- 新增**用户角色**可零改代码（`config/config.go:467-506` + `cmd/run.go:292`）——好。
- 工具面 enum 双源不同步：动态 enum 由 registry 派生（`tools/subagent.go:42-51`），静态回退 `handoffToolSpec` 手抄 6 个角色名（`engine/agent.go:375`）→ 回退路径下 config 角色不可见。
- 改法：删掉静态 enum 的手抄列表，改为由 registry 派生。

### 2.7 UI 按工具名特判渲染（①，历史 T2/T6 仍成立）
- `ui/model.go:46-53` `ToolNode` **无渲染元数据字段**；特判点 `:433-438`、`:575-580`、`:2402-2411`、`:2540`、`:2553`、`:2583`、`:2596`、`:562`（bash spinner）、`:425/:560`（`toolIcon`）。
- 失效场景：新工具落 default 桶（无图标/无 diff/无 output 子行）；改名需同步 6+ 处。
- 改法：`ToolSpec` 增声明式渲染元数据（品类/图标/是否 diff），UI 只读元数据。

## 4. ⚠️ 提示块剥离：用自然语言标题 + 空行当结构边界（③+②）

**仍是历史审计 §7.2 / §7.4-P5 的未闭合项，且过删面比历史记录更大。**

- 识别已改好（历史 T3 已修）：`engine/dsml.go:96-107` 从本轮真实注入块派生标题集合（`InjectedBlocks()`，`context/builder.go:59-67`），改提示词即自动同步；死条目不删除合法答案。
- **但边界语义未改**：`engine/dsml.go:146-152` 仍是"命中标题行 → 跳过，遇空行复位"，只吃掉标题（及紧邻非空行）。真实块形态恰是"标题 → 描述 → **空行** → 正文"：
  - `## 代码库结构`（`context/prompt.go:47-56`）：目录树（围栏）照旧漏给用户。
  - `## Available Skills`（生产者 `cmd/run.go:171-197`）：技能列表照旧漏出。
  - 测试已把该缺口固化为期望值：`engine/dsml_internal_echo_test.go:97-101`。
- **过删面（P5 + 新证据 N1）**：`InjectedBlocks()` 含 `systemPromptWithLang`（= `promptset/zh/system.md` 全文 + `# Language Pack` + examples），因此 `# 身份`、`# 核心规则（必须遵守）`、`## 始终做（无需确认）：`、`# 边界`、`## 环境` 等**通用标题全部成为删除触发词**；`context/builder.go:108-113` 还把 **AGENTS.md 正文**（用户文件，标题任意）并入派生集 → **不可控输入驱动确定性删除**：模型答案里写同名小标题，其后到空行的内容被静默删除。现有测试 `dsml_internal_echo_test.go:66-70` 用 `injected:nil` 断言 `# 身份` 被保留，**绕开了生产实情**，给了假阳性。
- **改法**：改为结构化边界——由生产者在注入块首尾写不可见哨兵/start-end 标记，剥离器按标记成段切除；或最低限度让 fixture 镜像真实生产者形态，使缺口在测试中可见。
