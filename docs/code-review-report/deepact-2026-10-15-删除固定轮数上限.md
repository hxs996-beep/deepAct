## 二、问题清单

### 🔴 严重

#### S1. `TokenBudget = -1`（显式无限）档位下，子 agent 循环失去任何终止边界 ✅
- **位置**：`engine/sub_agent.go:594`（`for ; ; iter++`）、`:754`（`if budget := tokenBudgetFor(input, r); budget > 0`）、`:1392-1407`（`-1 → 0`）、`:763-767`（80% 提示武装，与预算门同一个 `budget > 0` 块）、`:322`（Run 级预算只在准入检查）。
- **证据**：预算解析为 0 时，`budget > 0` 同时短路了**预算硬门**与**80% 收尾提示**（两者同块）→ 循环顶部 `:641-650` 的注入永不可达。而三击守卫全部挂 `len(ToolCalls)==0` 或被合法派发清零（`:938`、`:1029-1031`），因此「每轮都有集合内合法工具调用」的组合**结构上没有任何退出条件**（仅剩 ctx 取消 / LLM 报错）。
- **触发路径**：`[context] sub_agent_token_budget = -1` 或 `[agents.X] token_budget = -1`（**合法档位**，`config/config.go:423-428`、`:477-479`、`config_test.go:214-220` 锁定）→ 委派 researcher 等结构化角色 → 模型每轮 read 新文件且从不 submit → 无限运行；同步 `handoff_to_agent` 会挂住主 agent；Run 级树预算救不了（在途 run 不可见）。
- **与本次改动的关系**：HEAD 下同样的 `-1` 被四个内置角色的 15/20/20/5 轮硬上限兜住；本次删除后这最后一道兜底消失。
- **修复方向**：①`-1` 时仍保留一条与 token 无关的兜底（例如很大的轮数/墙钟上限）；②或让「无预算」时继续按可估算的上下文消耗武装 80% 提示；③或把 Run 级预算改为在途检查。**需用户决策**（`-1` 的语义是"知情地放弃保护"，还是"只放弃 token 顶"）。

#### S2. 主 agent 的「假 progress」可永久重置唯一守卫——删除 `MaxTurns` 后 Run 无任何上界 ✅
- **位置**：`engine/turn.go:1314-1317`（`case unclassifiable: progress = true`）、`engine/turn.go:1288`（`unclassifiable := !declared || !toolSemanticsKnown(spec)`）、`engine/turn.go:1243-1245`、`engine/guards.go:61-63`（`success && resetOnSuccess → delete + GuardAllow`）、`engine/loop.go:646-669`（唯一能终止 Run 的守卫）、`tools/mcp/tool.go:21`（MCP 工具**不声明**任何语义）。
- **证据**：未在注册表声明语义的工具（不存在的工具名、任意 MCP 工具）每轮都算 progress → `progressLoop.Check("", true)` 直接清零计数器 → 永不 nudge/block；而主循环已无轮数上限、也没有 token 兜底（`runUsageAccum` 只用于 eval/日志）。
- **触发路径**：模型每轮调用一个不存在的工具名（注册表返回 "tool not found" 错误并继续 turn），或反复调用同一个 MCP 工具 → `Run` 永不返回。默认配置即可触发，无需特殊设置。
- **与本次改动的关系**：`unclassifiable → progress` 是 HEAD 既有逻辑，本次删除 999 轮兜底后成为无界路径（子 agent 对同形态有执行门 + 3 击，主 agent 无等价物——存在不对称）。
- **修复方向**：①把 `unclassifiable` 的 progress 判据改为「按 `name+args` 签名只算首次」（复用 `progressKeys`）；②或让 MCP/未知工具声明语义；③或给主 Run 加一个成本上限作为最后兜底。

### 🟡 一般

#### M1. provider（或桩）不上报 usage 时，子 agent 唯一的硬兜底静默失效 ✅
- **位置**：`engine/sub_agent.go:755`（`spent = CacheMissTokens + CompletionTokens`）、`:754`；`llm/deepseek.go:830-838`（`usage := Usage{}` 零值）、`llm/adapter.go:204-210`（原样映射）。
- **证据**：无 usage 时 `spent` 恒为 0 → `spent >= budget` 永不成立 → 预算门与 80% 提示一起静默消失。仓库内直接证据：新增的回归锁 `engine/sub_agent_remove_turn_limit_test.go:32-66` 的脚本**不带 Usage**，100 轮 read 期间预算门一次未响，全靠脚本自带 `submit_result` 收尾——**该测试只证明"没有轮数上限"，不证明"预算能兜住跑飞"**。

- **修复方向**：检测连续 N 轮 usage 全零时用 token 估算折算（`llm` 已有估算器），或至少 fail-loud 记一条日志/进度告警，避免守卫静默失效。

#### M2. 两条「参数非法 → `continue`」路径不递增任何 strike 计数 ✅
- **位置**：`engine/sub_agent.go:877-891`（结构化 run 的 `submit_result` summary 为空/JSON 非法 → `:891 continue`，不动任何计数器）；`:946-953`（`ask_user` 参数非法 → `:953 continue`，而 `:938-939` 已置 `consecutiveBlocked = 0; dispatchedAny = true`，回合末 `:1029-1031` 又清零 `consecutiveIntermediate`）。

- **触发路径**：模型每轮返回 `submit_result` 且 summary 为空（测试里已有同形构造 `sub_agent_finish_test.go:232-239`），或每轮返回 `ask_user` 且 question 为空 → 无界（若同时 `-1` 则见 S1）。
- **修复方向**：无效调用计为一个 strike（≥3 → `loop_detected`/`no_result`），或最小改动——`:938` 不把「参数非法的 ask_user」当成 `dispatchedAny`。

#### M3. 「未交付」在状态通道被渲染为 ok/✓，与 digest 文案及注释的不变量冲突 ✅
- **位置**：`engine/loop.go:352-366`（`handoffResultStatus`：只有 `Blocked`/`cancelled`/`error` → error，其余 `"ok"`）、`engine/handoff.go:134-144`（同步路径同构）。
- **证据**：`budget_exceeded`（`sub_agent.go:757-761`）、`no_result`（`:797`）、`stalled_narration`（`:820`）、`loop_detected`（`:930-934`）、`max_tokens`（`:776`）**都不设置 `Blocked`** → 这些 run 在 UI/工具结果里得到 ✓，而同一个 digest 的标题写的是 "Sub-agent exceeded its token budget (partial result):"（`engine/agent.go:639-640`）。`loop.go:352-354` 的注释自称「a finished run must never render as a success when it did not deliver」，代码不满足该不变量。
- **触发路径**：子 agent 预算耗尽（删掉轮数上限后这成为「未交付」的第一大结局）→ async 路径发 `agent_done{Status:"ok"}`，同步路径 `ToolResult.Status="ok"`。
- **与本次改动的关系**：形态 HEAD 已存在（旧的 `max_iterations` 同样 `Blocked=false`），本次因 `TimedOut` 被删、`budget_exceeded` 成为主路径而放大。
- **修复方向**：状态映射改为按 `FinishReason` 的排除表（与 `isHandoffFollowUpReason` 同口径）；或把这些 reason 也置 `Blocked=true`（会改变 `Blocked` 的既有含义，**需产品确认**）。

## 五、结论与建议

本次改动**方向正确、实现干净**：删除的是一整类「逐角色写死轮数」的场景枚举，残留引用为 0，编译/测试/gofmt/vet 全部通过，且符合 AGENTS.md 的泛化性与能力优先原则。

但「统一到通用机制」的**前提没有被完整兜住**，出现两个严重缺口和一个一般性隐性失效：

1. **S1**：`-1`（合法档位）下预算门与收尾提示一起消失，子 agent 结构上无界——这是"删掉兜底后才发现兜底还在被依赖"的典型。
2. **S2**：主 agent 的 progress 判据可被未声明语义的工具（含 MCP）永久伪造，删掉 999 后主 Run 无上界。
3. **M1**：预算门依赖 provider 上报 usage；不上报时唯一硬兜底静默失效——**本次新增的回归测试恰好是这种形态，因此它不能作为"预算能兜住跑飞"的证据**（这是审查中最值得记住的一点）。
4. **M2/M3** 是同一主题的两个侧面：收敛边界的"边界点"与"结局表达"仍有缝隙（无效调用不计击、部分结果被标 ✓）。

**建议处理顺序**：S1（需决策）→ M1（加 usage 兜底/告警）→ S2（progress 判据按签名去重）→ M2（无效调用计击）→ M3（状态映射按 reason）→ L1（配置键 fail-loud，需决策）→ L6/L8（本次引入的文档与测试质量，低风险可直接改）→ 其余按需。

**审查可信度**：S1/S2/M1/M2/M3/L1/L3/L6/L8 的行号与代码证据均由主 agent 独立读码核实（✅）；L2/L4/L5/L7/L9 为代码证据成立但严重度判定为「轻微/建议」；L10 为方向性建议。所有"测试通过"结论来自实际执行，不是推断。
