## 6. 代码审查结果

### 🚨 Critical

#### Issue 1：多行输入时"拖选高亮"与"复制内容"不一致（复制文本左移「前置换行数」个 rune）

- **文件**：`ui/input_selection.go:86-97`（`inputRowRuneAt` 行偏移累加）、`ui/model.go:3343-3344`（`caretStart` 累加）；受影响的换算对：`ui/input_selection.go:133-153`
- **置信度**：**95**（已由主 agent 可执行实证复现，非静态推断）
- **严重级别**：Critical（新能力的核心契约"拖选哪段就复制哪段"在含换行输入下必然失效）
- **来源**：🔴 本次引入
- **描述**：
  `inputRowRuneAt` 用「前若干绘制行的 `utf8.RuneCountInString` 之和」作为行首偏移。但 `wrapInputText` 会以真实 `\n` 切分行（`ui/model.go:3362-3405`），被切掉的 `\n` **不**计入任何一行的 rune 数，而 `caretToBufferIndex`/`bufferToCaretIndex` 明确工作在"含 `\n`、含 caret 的绘制文本空间"。两个空间在每个真实换行处相差 1，于是：行首映射比正确值**小「前置换行数」**。
  高亮路径恰好自洽（`bufferToCaretIndex(from) - rowStart` 两侧同源错位，相互抵消），因此**高亮显示正确、剪贴板内容错误**——用户看到选中了 "ef"，剪贴板里却是 "d\n"。
- **复现与实证**（临时测试，运行后已删除）：

  ```go
  m.inputBuf.SetValue("ab\ncd\nef")   // 8 runes，cursor=8
  m.inputRuneAt(top+2, 5)  // → 2，期望 3（'c'）
  m.inputRuneAt(top+3, 5)  // → 4，期望 6（'e'）
  // 在第 3 行 "ef" 上从行首拖到行尾：
  //   anchor=4 focus=6
  //   copied = "d\n"              ← 剪贴板
  //   rendered = "…▍    \x1b[7mef\x1b[27m█…"   ← 高亮落在 "ef"
  ```
- **可达性**：`Alt/Shift+Option+Enter` 插入换行（`ui/input.go:884-911`）、未折叠的粘贴内容、以及本次新增的 `↑` 召回（`SetValue(lastSubmittedInput)`，历史可能是多行）都会产生含 `\n` 的 buffer。**单行输入不受影响**（无 `\n` 时两空间重合），这正是既有 16 个用例全绿的原因。
- **修复建议**：统一索引空间。最小改法——在行偏移累加时把被消耗的真实换行补回来：

  - `inputRowRuneAt`（`ui/input_selection.go:86-89`）：跨过的每个**真实换行**额外 `+1`（硬换行不 +1）。可由 `inputTextWithCaret()` 的真实 `\n` 个数推出每行末尾是否为真实换行，或用与 `renderInputLine` 完全同源的"行起点表"。
  - `ui/model.go:3343-3344` 的 `caretStart` 同步修正（两者必须共用同一个行起点计算，建议抽成一个 `inputRowStarts()` 供渲染与命中测试共用，从根上消除"两份行偏移逻辑"）。
  - 回归测试：`SetValue("ab\ncd\nef")`，在第 2 行拖选断言得到 `"cd"`、在第 3 行拖选断言得到 `"ef"`。

  > 更彻底的做法是让"行起点表"直接由 `wrapInputText` 返回（它才知道每行是被 `\n` 还是被硬换行切断），避免第二次推导。

## 7. 补充分析

### 7.1 逻辑模拟（dry-run）结论摘要

| 场景 | 结论 |
|---|---|
| 输入框内单击（press→原地 release） | ✅ 无残留选区、无假反馈 |
| ASCII / CJK / 硬换行跨行 / 从分隔行起拖 / 反向拖 | ✅ 高亮与复制一致 |
| **含真实 `\n` 的多行拖选** | ❌ 复制内容左移（Issue 1，已实证） |
| 拖出输入框后 release | ✅ clamp 到边界，行为确定（属设计选择，见 #10） |
| 两种选区互斥（正文↔输入框互相按下） | ✅ 无同时残留 |
| 选区 Done 后按键 / resize / 流式更新 | ✅ 按键清除；resize/流式保持（索引与屏幕坐标解耦） |
| ↑ 全分支（空框/草稿/无历史/空白提交/resume/options/suggestions/PasteMode/steer） | ✅ 守卫与顺序均正确 |
| 剪贴板写入失败 / 空选中 | ✅ 反馈与实际一致（`reportCopy` 三分支自洽） |

### 7.2 错误处理审查

`copyText` 的 `("", nil)` 约定被两个调用方正确转发；`reportCopy` 三态成对写入 `clipboardError`/`clipboardFeedback`，无状态互污；`copyToClipboard → pipeToCmd/windowsCopy` 全程传播错误，无被吞掉的 error、无空错误处理器。`clipboard_other.go` 的 `return nil` 是不可达的 build-tag 桩，非静默失败。

### 7.3 类型与不变量

`Active && Done` 不可达、`Anchor ≤ Focus` 由 `normalizeInputSelection` 交换、索引越界由 `caretToBufferIndex` clamp 兜住 —— 三项不变量在现有写入点下均成立，未发现破坏运行时行为的类型缺陷。主要短板是"三种索引空间全为裸 `int`，仅靠注释区分"，Issue 1 正是该表达缺失的直接代价。

## 11. 审查总结

**方向正确，但不能直接收尾。**

- 改造的三件事都是真实需求：修复了一个"假成功反馈"缺陷，新增了输入框拖选复制与 ↑ 召回两项能力，架构上属于 AGENTS.md 推崇的"能力通道"，未引入场景启发式，改动收敛在 `ui/` 包内，无公开 API 破坏，构建/静态检查/现有测试全部通过。
- 但新能力存在 **1 个必现的正确性缺陷**（Issue 1）：输入含真实换行时，"高亮所见"与"剪贴板所得"不一致（实证：高亮 `ef`，剪贴板 `d\n`）。原因是行偏移累加漏算被 `\n` 切掉的换行 rune，而索引空间只在注释中约定、未在类型或单一函数中收敛。单行输入（主路径）不受影响，因此既有 16 个新用例全绿掩盖了它。
- 其余问题中，2 处是"注释/文档与实际不符"（popup 守卫、README），6 处是测试覆盖与测试质量问题，均低风险。
- 处理建议（按优先级）：① 修 Issue 1 并补其回归测试；② 补复制失败路径与 PasteMode 两项测试；③ 修正 popup 注释或守卫、同步 README；④ 其余 Low Confidence 项按需处理。
